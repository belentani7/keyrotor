Cómo funciona

Tres reglas,
cero secretos expuestos.

Arquitectura proxy local: el frontend habla solo con keyrotor; jamás ve una clave ni llama a proveedores directamente.

NO SECRETS

Ninguna clave real entra en git, logs, métricas ni UI. Todo texto pasa por el redactor antes de imprimirse: claves enmascaradas sk-a****34.

Backend proxy

El dashboard solo ve GET /api/status y POST /v1/chat/completions. Cero llamadas directas a OpenRouter, NVIDIA, Google u OpenCode desde el navegador.

Rotación sin downtime

Pool de claves primarias + fallback por proveedor. 401/403 descarta la clave y reintenta con la siguiente. Failover entre proveedores automático.

Retries + backoff

429/408/5xx reintentan con backoff exponencial + jitter sin descartar la clave. Errores de red tampoco descartan.

Cortacircuito

5 fallos consecutivos abren el circuito 60 s; sonda half-open tras cooldown. Éxito cierra, fallo reabre.

Caché TTL

Hash exacto SHA-256(proveedor + URL + body) con TTL por proveedor (por defecto 300 s). Repetición idéntica = 0 tokens.

Local por defecto

Binding solo en loopback (127.0.0.1, ::1). CORS restringido: rechaza Origin cruzado. Para API pública hace falta auth, HTTPS, límites y gateway.

CLI + Dashboard

python -m keyrotor chat "hola", python -m keyrotor status. Dashboard en http://127.0.0.1:8000/ con claves enmascaradas.

FAQ

Preguntas frecuentes

¿Cómo cargo las claves si no uso .env?

Las claves se leen exclusivamente desde variables de entorno del proceso. En Windows PowerShell: $env:OPENROUTER_API_KEYS='sk-...'. En Linux/macOS: export OPENROUTER_API_KEYS='sk-...'. El archivo .env.example es solo referencia local; no se carga automáticamente.

¿Qué pasa si una clave devuelve 401/403?

La clave se marca como muerta, se descarta del pool y se reintenta con la siguiente clave del mismo proveedor. Intentos ilimitados hasta agotar el pool de ese proveedor.

¿Cómo funciona el failover entre proveedores?

Si un proveedor se queda sin claves, tiene el circuito abierto o devuelve error 4xx, el router pasa automáticamente al siguiente del KEYROTOR_PROVIDER_ORDER (por defecto: openrouter,nvidia,google,opencode).

¿Los errores 429/5xx descartan la clave?

No. 429 (rate limit), 408 (timeout) y 5xx se reintentan con backoff exponencial + jitter sin descartar la clave. Errores de red tampoco descartan.

¿Qué es el cortacircuito y cuándo salta?

Tras 5 fallos consecutivos (umbral configurable con KEYROTOR_BREAKER_THRESHOLD) se abre el circuito por 60 s (KEYROTOR_BREAKER_COOLDOWN). Pasado el cooldown se envía una sonda half-open: éxito cierra el circuito, fallo lo reabre.

¿La caché usa claves reales en el hash?

No. El hash es SHA-256(proveedor + URL + body) — sin claves. TTL por proveedor (por defecto 300 s con KEYROTOR_CACHE_TTL). Una repetición idéntica cuesta 0 tokens y no toca la red.

¿Puedo exponer keyrotor en 0.0.0.0?

No por defecto. El servidor solo hace binding en loopback (127.0.0.1, ::1). Para API pública es imprescindible diseñar antes: autenticación, autorización, HTTPS, límites de uso y un gateway. Esta versión no debe abrirse en 0.0.0.0.

¿Cómo verifico que no hay secretos en el repo?

Ejecuta python scripts/secret_scan.py — recorre el repo buscando patrones de claves (OpenAI, OpenRouter, NVIDIA, Google, JWT, GitHub PAT, HF, AWS…). El CI lo ejecuta en cada push.
